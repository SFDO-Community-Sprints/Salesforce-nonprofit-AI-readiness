# Reference app review and improvement backlog

Read-only inspection on 21 October 2026 of the reference Salesforce AI Readiness app. This is a comparison of visible behavior, not a source-code audit or verification of the reference app's scoring/security. No scan, save, deployment or data mutation was performed in the reference org.

## What was observed

- **Home:** separates passed, failed and unknown results across its defined checks. The visible summary showed 51 defined checks: 13 passed, eight failed and 30 unknown. Those are reference observations, not our app's results.
- **Org Scan:** showed 39 checks (11 passed, five failed, 23 unknown), a saved run reference, timestamp and actor. It has All, Needs attention, Not checked, Passed and Critical filters, a category selector and collapsible category groups. Findings expose “Why and how to fix” and link manual gaps to “Answer in Checklists”. The different Home/Org Scan totals require scope explanation rather than assuming they share a denominator.
- **Company checklist:** presents a stage rail for Responsible people, Staff readiness and Privacy. Responsible people includes privacy/DPO responsibility, security owner, Salesforce administrator, other stakeholders and an explanation when a DPO is not legally required.
- **Org checklist:** presents category stages. Questions offer Yes, Partially, No and Not sure, plus notes, responsible person, due date and expandable advice. Persistence and scoring behavior were not exercised.
- **Implementation checklist:** selects a registered use case; stages cover AI access, data quality, safeguards, staff and privacy. AI access asks for the actual integration username and offers Use this user and Run checks again. These actions were not executed. Visible check topics include effective broad grants, sensitive-field access, API-only identity, declared grounding scope, completeness, blank/Other picklists, freshness, free text, similar fields and metadata descriptions.
- **Use Cases:** lists business owner, lifecycle status, score, checks completed, health and critical failures. Its unsaved new form includes intended integration-user lookup, data scope, one `Object.Field` grounding field per line, added value, success criteria, risks/losses, mitigation, handover points, costs, gains and cost-versus-gains notes.
- **Saved assessment and AI Use Cases object tabs:** present in navigation. A saved assessment link was visible; record details, immutability and standard use-case object details were not inspected. No Settings tab was visible.
- **Home guidance:** warns to register a dedicated AI connection instead of using System Administrator and shows scan age. The reference uses a 24-hour warning; that is not automatically an approved policy for our app.

## What to reuse in our implementation

Keep the native Apex collectors, real input/configuration measurements, separate score and coverage, explicit unknown states, specialist permissions and existing Overview/category tabs. Extend those components rather than replacing them with another dashboard or a copy of Salesforce Security Health Check.

`ReadinessOrgHealth` already supplies the health result and actual/expected/action rows. `readinessOrgHealth` already displays a last-scanned timestamp. `ReadinessStaffReview` already saves versioned staff snapshots. `Readiness_Operation__c` stores fixed sanitized events; it is not a complete saved health report. These are starting points, not evidence that the following work is complete.

## Proposed build order and acceptance criteria

The native implementation now includes these six feature families. Deployment and validation evidence is tracked in [the workspace guide](implementation-workspace.md) and [TODO](../TODO.md); this review is not itself a completion claim. They extend the [sprint requirements](project-notes.md), and do not replace the outstanding real-assistant, external-erasure or human acceptance work in [TODO](../TODO.md).

1. **REF-1: Name the implementation and actual AI connection.** Add a use-case/implementation record with business purpose, accountable owner, intended assistant/integration identity, allowed objects/grounding fields/actions, excluded actions, value/success criteria, costs/gains, risks/mitigation and handover/stop responsibility. Scope applicable findings to the selected implementation. Acceptance: two implementations can retain different scopes; an admin's successful test never passes the intended assistant's test; missing identity/scope remains unknown. Validate object/field identifiers against accessible metadata and bounded collector support; never concatenate free text into SOQL. Store references and scope, never passwords or tokens.
2. **REF-2: Separate Company, Org and Implementation checklists.** Add the named-person and policy questions from the project notes, with a short staged flow, advice and Yes/Partially/No/Not sure responses. Reuse the existing seven observed staff exercises for competency. Acceptance: answers survive reload and remain bound to the correct scope; Not sure is unknown; reported policies cannot overwrite executed observations or count as demonstrated human competency; missing DPO designation asks for the appropriate privacy owner and explanation without declaring legal compliance.
3. **REF-3: Make gaps accountable.** Add responsible person/role, due date, notes and evidence reference per applicable manual answer or remediation. Acceptance: permitted reviewers can edit only their authorized scope, changes retain author/time, overdue and unassigned items can be found, and scanning never creates Tasks without explicit authorized action. Keep free-text evidence out of the aggregate MCP response. Distinguish a business lifecycle status such as Approved from measured Blocked or Incomplete readiness; include accountable approver and named stop/handover responsibility.
4. **REF-4: Save comparable scan history.** Persist versioned, sanitized report snapshots with time, actor, selected scope, rubric version, passed/failed/unknown totals and coverage. Acceptance: a later scan does not rewrite an earlier result; comparisons identify scope/rubric changes; no raw donor records, emails or staff evidence are stored in the health snapshot; missing permissions remain unknown. Reuse existing operational events for probes rather than misrepresenting them as full snapshots.
5. **REF-5: Make findings easy to work through.** Extend the existing Overview table with outcome/severity/category filters, category grouping, expandable plain-language advice and links to the exact checklist question. Acceptance: counts and denominators explain their selected scope; filters preserve scan state; keyboard and screen-reader navigation work; Actual/Expected columns retain equal width; Overview keeps AI readiness findings and existing detail tabs remain available.

6. **REF-6: Expand bounded, use-case-specific collectors.** Start with effective profile/permission-set/group broad grants, object sharing/guest access, sensitive-field classification and grounding metadata descriptions; then extend per-object completeness, duplicate/orphan indicators and approved freshness policies. Reuse native collectors and narrowly scoped reader roles. Acceptance: every check has an explicit scope, denominator, threshold, timestamp and pass/fail/unknown fixtures; denied/inaccessible metadata remains unknown; metadata inventory does not pass actual assistant runtime safeguards; no new broad grants are added simply to collect a score.

## Reference rules to assess critically

The visible reference rubric included an API-access pass at 80% of active users, a broad-access pass despite three broadly privileged users, a failure for missing muting permission sets, and a temporary-restriction pass based on session-based permission-set existence. These rules were observed, not validated or endorsed. Avoid copying arbitrary thresholds or treating feature presence as control effectiveness. Missing muting is not automatically a vulnerability. No connections/external users may be not applicable for a specific scoped check, but never proves an AI connection safe. DPO/legal and provider-policy claims require separate fact-checking.

Each implementation item requires focused Apex permission/behavior checks and rendered UI validation. Demo seeds may create fictional input records and configuration only; they must never insert readiness scores or fabricated test passes.

## Inspection limits

Visible controls do not prove persistence, API contracts, authorization, score correctness or actual runtime safeguards. The use-case registration form was canceled without saving. Standard object record details, saved history behavior, actual integration-user execution, alert delivery, assistant stop, end-to-end erasure, mobile and accessibility were not validated. No reference metadata was retrieved or copied, and no reference org readiness conclusion is made.
