# Versioned readiness check specifications

[check-specifications.json](check-specifications.json) catalogs all 16 checks in `donor-summary-demo-v1`: four aggregate data checks, five technical controls and seven staff exercises. It records stable IDs, categories, rubric critical gates, severity, applicability, required evidence, measurements, acceptance criteria and specification/test revisions. It does not change the scorer, approve a customer profile or supply missing evidence.

Data thresholds and priority thresholds mirror `demo/rubric.json`. Contact presence/linkage and repeated-email indicators are deliberately narrow measurements, not proof of accuracy, consent or correct relationships. Live small cohorts remain suppressed and unknown. The explicit local synthetic override remains a demonstration only. Staff action and critical-failure IDs reference `staff-answer-key.json`; the catalog does not replace that answer key. Severity distinguishes rubric gate failures from the staff evaluator's explicit observed critical-failure markers.

Query/test version values identify these specification revisions. They are not runtime collector tags or evidence of completed runtime tests. Implementation and test paths identify where the current behavior is defined and checked. Existing technical scorer tests exercise fixtures; all five live technical controls remain unknown pending approved observations under the intended identity. End-to-end privacy/erasure remains a separate High-priority unknown outside scored categories and simulated pilot decisions.

Run `python3 -m unittest discover -s scripts -p test_check_specifications.py` to check catalog coverage, gate membership, data acceptance boundaries, threshold alignment, staff action IDs, implementation/test paths and the unknown-control/privacy boundary. Existing rubric replay and runtime tests remain necessary; this catalog's tests do not replace them.

When definitions change, revise the relevant specification version and retain the old rubric, specification and evidence with historical results. Any customer-approved thresholds, applicability exclusions and freshness policies must be recorded as separate versioned policy evidence. Current native and restricted MCP aggregate assessment outputs include `specification_version` and `profile_overrides: {}` for the fixed rubric. The native resource `CheckSpecifications` mirrors this catalog, with byte parity checked locally. Empty overrides explicitly record that no overrides were applied to these outputs; they do not implement custom profile support. Historical synthetic expected snapshots remain unchanged for replay. The fixed profile does not expose caller-supplied overrides, arbitrary check identifiers, fields or queries; attaching metadata does not expand collection permissions. Customer-approved policies and future override execution remain separate work.
